## Required fix

**B-SOURCE-01 — non-ASCII whitespace in endpoint schemes has different Rust/C# admission (PARITY/API/VALIDATION; all eight items through their respective factories).**

The Rust factories accept leading/trailing Unicode whitespace in a scheme because they call Unicode-aware `str::trim()` before ASCII-case comparison:

- `instrument-components-keysight/src/qualified_scpi.rs`, `endpoint` (around line32): `endpoint.scheme.trim().eq_ignore_ascii_case("scpi")`.
- `instrument-components-keysight/src/hp34980.rs:58`, `endpoint`: same `scpi` logic.
- `instrument-components-keysight/src/hp3585.rs`, constructor and `selected`: use `tx::validate_endpoint`.
- `instrument-components-keysight/src/message_backend.rs:209`, `validate_endpoint`: same trimming pattern for`hpib`.

Conversely, C# `QualifiedScpiFactory.EndpointValid`, `Hp34980Factory.EndpointValid` and `Hp3585Factory.EndpointValid` explicitly reject any non-ASCII character in the complete scheme before trimming. For example, a binding scheme consisting of NBSP followed by`scpi`, or`hpib` followed by U+2003 EM SPACE, is accepted by the corresponding Rust constructor but rejected with InvalidArgument by C#. Rust's endpoint key also trims those Unicode characters, so they become an admitted alias for the ordinary scheme. This is a concrete cross-language admission difference, not a hypothetical issue in unrelated runtime discovery.

Align the new factories to one policy consistent with the approved ASCII scheme contract. An explicit ASCII check before Rust trimming is consistent with current C#. Keep ordinary ASCII whitespace trimming/case behavior. Add actual constructor/open procedural cases for leading and trailing NBSP/other Unicode whitespace, asserting matching typed rejection and zero connector acquisitions in both languages. Preserve existing native HP drivers' behavior unless separately authorized by their contracts; a3585-local admission check can avoid broadening this change to old factories.

This finding was reported immediately. The facilitator confirmed the discrepancy and described a planned fix/tests; **that evolving change is not present in or verified against this frozen packet**. Retain this finding until a later frozen revision demonstrates the correction.
