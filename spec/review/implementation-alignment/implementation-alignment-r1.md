## Evidence blocker identified and reported promptly

The first new delayed-host deadline proofs in `validation/rust/src/hp_async_proof.rs` and `validation/dotnet/HpAsyncProof.cs` sleep/delay20ms and then explicitly return/throw Timeout. This is delayed injected Timeout. It proves typed propagation/quarantine/no retry, but does not prove that a genuinely stalled write/read/incomplete response is terminated by a separate finite deadline. V9 expressly requires a real stalled-response deadline test. The parent agreed and is replacing these branches with independent deadline control around genuinely pending IO, plus generic QueryBody byte-transport incomplete-frame tests. The replacement proof has now been inspected; see the targeted recheck below. This was an acceptance-evidence gap, not a vendor parser/state defect.

The replacement should establish stalled RF write as well as pending/incomplete read, or explicitly map a concrete generic write-deadline test. The inspected first Host Write/WriteAsync methods always complete; read-only expiry cannot alone prove bounded stalled writes. Verify active access ends on expiry, the first error remains Timeout, later invocation fails SessionNeedsRecovery before IO, and no retry/drain/device command follows. Positive finite constructor/connector deadline validation and response allocation bounds belong to the actual connector composition, not to a sleep-based test double.

## Nonblocking representation/documentation differences

3497 public input configuration derives native address from slot/local; it does not expose a separately supplied native field that can contradict20*slot+local. This eliminates the invalid redundant state, but differs from the literal v9 wording/matrix about validating a supplied native address. Clarify this as unrepresentable by construction rather than claiming a nonexistent negative test was executed. Both3497factories additionally impose a4096endpoint limit; RF specifies that bound, while the3497 document does not name it. Document the extra3497 bound as a software policy. Neither difference changes wire/topology safety or the scoped semantic operation.

The shared message layer checks body size after the host returns an allocated string; actual pre-allocation limits, clean complete framing and finite host deadlines must therefore be proven in the commissioned connector. README describes that dependency. A compliant-host composition proof can establish it; the backend itself cannot enforce those promises on arbitrary custom MessageIo implementations.

## Concrete connector integration blocker: binary framing can hide malformed native data

The first generic QueryBody/query_body implementation reused SCPI ReadResponse framing, which recognizes IEEE488.2 block headers and returns only block payload. That violates the HPexact-native-body host contract: only CRLFframing may be removed, and binary responses must be rejected. A malformed block wrapper can otherwise become an accepted scalar/state/token before the HPparser sees it.

I reproduced against the actual main C# ScpiSession with the scratch app `query-body-block-repro/Program.cs` (dotnetrun net8.0 exit0):

* Wire `#211+1.25000E+0\r\n` became QueryBody `+1.25000E+0`, which satisfies3497's strict voltage parser and reports1.25V.
* Wire `#110\r\n` became QueryBody `0`, which satisfies RFoutputOFF verification.

Rust query_body likewise passed through read_response/try_extract_response's block branch. This is a connector/framing integration defect, not a weakness detectable by a vendor parser after its input wrapper has already disappeared. It was reported immediately. The parent confirmed and is adding a plain-text default that rejects initial'#' before SCPI block interpretation, including fragmented/full#0/#110/#211 cases on all session paths. OrdinarySCPIQuery binary behavior remains separate. The standardVISAconnector retains explicit allowBinaryBlocks compatibility for existing waveform profiles; HPcomposition must passfalse. README now records endpointSchemehpib,maxResponseBytes256,CRLF,allowBinaryBlocksfalse. The fix was independently inspected: all four session paths reject a leading#before any block framing interpretation, including a split first-byte reply. C#plain-text mode is the QueryBodydefault; genericVISA can explicitly retain block support for other standardprofiles, while documentedHPcomposition requiresallowBinaryBlocksfalse. Visa regression maps that rejection to typedParse after one read. The concrete integration blocker is now closed on the inspected current code. Full final regression/packed evidence must still be retained at the finalSDK/source identities.
